*   **Render Deployment**: Prototype web service successfully deployed from `main` branch to Render and confirmed Live.
*   **Duda Test-Site Verification**: Client-side listing and detail rendering manually verified on the Duda test-site.
*   **Admin CMS Foundation**: Modular Next.js app structure, TypeScript domain models, and migrations `0001` - `0026`. Migrations `0010` - `0021` established atomic import, review, participant-preview, correction, publication, removal, and metadata-audit foundations. Migration `0022` added controlled staff identity provisioning; Migration `0023` added participant preview email delivery; Migration `0024` added explicit participant preview reminder scheduling and bounded due claiming; Migration `0025` forward-redefines the authoritative metadata, review-submission, review-action, and publication-readiness functions to require accessible poster content. Migrations `0001` - `0025` remain unchanged, and migrations `0007` - `0026` are unapplied to hosted staging.
*   **Secure Participant Preview**: After a project reaches `approved`, authorized staff (the existing `projects.review` permission — admin/reviewer) can generate a private, token-protected, time-limited (7-day default) participant preview link from the project detail page, and revoke it.
*   **Participant Confirmation**: Beneath the rendered preview, a participant may explicitly confirm — via a plain same-origin POST form — that the project information shown in this exact preview version is correct.
*   **Participant Correction Requests**: As the mutually exclusive alternative to confirmation, a participant may instead submit a plain-text correction request describing what needs to change about the exact preview version shown.
*   **Admin Correction Resolution & Controlled Preview Reissue**: Authorized staff holding combined `projects.edit` AND `projects.review` authority can start administrative resolution on an `open` participant correction request via the service-role-only `start_participant_preview_correction_resolution` RPC (Migration 0016). Starting resolution atomically revokes Preview A, transitions project status from `approved` to `changes_requested`, records an auditable `approval_records` entry, and sets request status to `in_progress`. When edits are ready and project status is reapproved, staff reissues a preview (`isCorrectionReissue = true`), capturing a fresh snapshot for Preview B and transactionally setting correction status to `resolved` with `replacement_preview_id` referencing Preview B.
*   **Publication Readiness Gate**: Service-role-only `get_project_publication_readiness` RPC (Migration 0017) evaluates authoritative publication eligibility. A project is publication-ready ONLY IF status is `approved`, exactly one active preview exists, that exact preview is confirmed by the participant, has ZERO unresolved or open correction requests, and current canonical participant-facing project metadata and authoritative private media match the confirmed preview snapshots (order-independent media comparison). `compilePublicFeed` is hardened to include `published` projects ONLY (`approved` projects are no longer feed-eligible). Readiness is rendered read-only on the project detail page. Actual publication, Duda upload, and public storage writes are not performed.
*   **Publication Preparation Plan**: Admin-only, server-authoritative dry-run preparation verifies fresh publication readiness, resolves deterministic final public-media URLs, compiles existing published projects plus one exact READY approved candidate through the public allow-list, validates the proposed artifact, and reports deterministic count/hash with exact confirmation evidence. The UI remains plan-only and performs no publication write.
*   **Controlled Publication Execution Foundation**: A server/core coordinator binds fresh readiness and final artifact evidence to a durable globally exclusive attempt; promotes verified private media without deleting its source; protects/restores the prior canonical feed around verified upload; and atomically commits project status, public media mappings, one `publish` audit, one snapshot, and the completed attempt. Sequential/concurrent retry and failure compensation are fail-closed. The Admin/CMS exposes this only as explicitly acknowledged Local test publication against a proven loopback Supabase endpoint. Hosted rollout, Duda action, email, long-term feed history, and administrative rollback are not included.
*   **Controlled Local Archive / Public-Feed Removal**: Admin-only Local execution reserves the same global feed-operation slot as publication before reading its baseline, binds and verifies the exact candidate feed and previous bytes, removes one published project from the canonical Local feed, and atomically archives it with one audit record. Generic `published` archival is rejected, zero-record feeds are supported, failures restore the exact prior feed, and public/private media evidence is preserved. Hosted/production mutation, Duda verification, media deletion, restore/republish, and completion of the later public-removal verification workflow remain out of scope.
*   **Participant Preview Email Notification — Local/disposable technical foundation implemented**: Staff holding participant-preview authority may explicitly choose *Generate preview and send email*, which emails the exact freshly generated secure link to the project's authoritative `projects.participant_contact_email` (Migration 0023), supplied through the canonical `project-details.xlsx` → parser → import staging path. One transaction validates the recipient, creates the preview from its hash alone, and reserves a delivery lifecycle bound to that exact `participant_preview_id`, so an active preview can never exist without one. The raw credential remains non-persistent: it exists only in server memory and in the outgoing message, is never stored, logged or recoverable, and therefore a delivery **cannot** be retried later for the same preview — staff issue a new preview instead. The ledger records `reserved → transport_started → sent`, plus `failed` and `delivery_unknown`, under a two-minute fenced execution lease whose terminal states are immutable; an expired lease never re-grants execution, and an ambiguous post-transport outcome is reported truthfully and never resent. Exactly-once delivery is explicitly **not** claimed. Ordinary Generate Without Email is unchanged and sends zero mail. Verified on Local Supabase with 54 runtime scenarios against the Local email sink, plus 100 unit/service tests covering escaping, header safety, transport classification, ownership fencing and ambiguous outcomes. **Still pending: institutional/provider approval, production SMTP or provider selection, production credentials, an approved From address and domain, institutional email policy, hosted/staging rollout, human UAT, and reminder policy. Real delivery is disabled by default and fails closed until explicitly configured server-side.**
*   **Initial Admin Authentication Activation (Staging)**: Initial administrator authentication operationally verified in isolated staging (`capstone-admin-cms-staging-2026`).
*   **Transactional Review Actions**: Atomic PostgreSQL RPC function `public.perform_project_review_action` (Migration 0008), repository integration, API route handler, static contract tests, and comprehensive local atomicity/rollback verifications implemented and merged into `main` via PR #36.
*   **Import Batch Review Readiness & Submit-to-Review**: Server-authoritative readiness derivation surfaced on `/admin/imports/[batchId]` and project detail page. Authorized preparation staff (`projects.edit`) can select ready projects and submit them for administrative review (`draft`/`changes_requested` → `submitted`).
*   **Accessible Poster Full Text — required across the production workflow**: `project-details.xlsx` now requires both `Poster full text` (`posterText`) and `Accessibility text` (`accessibilityText`); a missing column, a blank value after trim, an unusable formula cell, or a value beyond its bounded technical ceiling is a blocking workbook error. Staff can edit both in the existing Project Metadata editor under unchanged Admin/Editor authority, stale-version protection, approval-reopen gate, and published lock, and each field diffs independently into exactly one `update_metadata` audit record. Migration 0025 forward-redefines `update_project_metadata`, `submit_import_projects_for_review`, `perform_project_review_action`, and `get_project_publication_readiness` so a blank value blocks review submission (`MISSING_POSTER_TEXT` / `MISSING_ACCESSIBILITY_TEXT`), blocks approval (`ACCESSIBILITY_CONTENT_REQUIRED`, zero status and zero audit mutation), and blocks publication readiness independently of any stored preview evidence. The participant preview renders both values before the confirmation controls, and public-feed validation rejects a public record missing either. A legacy `project.json` package may still be staged without them but cannot progress until staff supply both. **No OCR and no AI**: both values are staff-authored or imported, and nothing derives, transcribes, scores, or generates them. **Still pending: per-snapshot/gallery alt-text completeness (no authoritative per-media alt-text field exists today), final Duda accessibility acceptance, formal WCAG conformance evaluation, and human accessibility UAT. This work supplies required accessibility content; it is not a WCAG certification or a professional accessibility audit.**
*   **Snapshot Image Alt Text — required across the production workflow**: The one snapshot image the repository recognises (`snapshot-1.png`, at most one `snapshot_image` row per project) now carries an authoritative staff-authored text alternative on `media_assets.alt_text_public`. The column is nullable and bounded at 2,000 characters, permitting NULL for poster media and for legacy snapshots awaiting correction, and **no existing row is backfilled**. `project-details.xlsx` gains a conditionally required `Snapshot image alt text` column with deterministic aliases: required only when the package actually contains `snapshot-1.png`, so a project without a snapshot image is never asked to describe one. Media staging derives the value from the server-reparsed package and binds it into `computeCanonicalMediaIntentHash`, so the browser can never supply it independently and a changed alt yields a different authoritative intent. Migration `0026` forward-redefines `finalize_browser_import_media_stage`, `submit_import_projects_for_review`, `perform_project_review_action`, `generate_participant_preview` (6-argument), and `get_project_publication_readiness`, and adds a service-role-only `update_snapshot_image_alt_text` RPC with Admin/Editor authority rechecked in the database, reviewer denial, the shared project `updated_at` stale boundary, `NO_CHANGES` semantics, approval-reopen and published locks, and exactly one typed `media_accessibility` audit record per successful edit. A missing alt blocks review submission (`MISSING_SNAPSHOT_ALT_TEXT`), blocks approval (`MEDIA_ACCESSIBILITY_REQUIRED`, zero status and zero audit mutation), fails participant preview generation closed through both the 6-argument generator and the legacy 5-argument wrapper and notification composer, and blocks publication readiness independently of any stored preview evidence. The alt is captured in the immutable participant media snapshot and participates in the media-snapshot comparison, so editing it after confirmation yields `MEDIA_SNAPSHOT_STALE`. Participant HTML now renders the snapshotted poster `accessibilityText` and snapshot `altText` as the `alt` attributes and **no longer falls back to the filename**; the Admin preview states "Snapshot alt text missing" instead of showing a filename-derived substitute. The public feed keeps `snapshots: string[]` unchanged for the existing Duda prototype and adds an additive structured `snapshotMedia: [{ url, altText }]` pairing, validated for exact URL correspondence, non-blank bounded alt text, and strict key allow-listing. **No OCR and no AI**: the value is staff-authored, and nothing derives, transcribes, scores, or generates it. **Still pending: arbitrary multi-image gallery support, Duda-side consumption of `snapshotMedia`, final Duda accessibility acceptance, formal WCAG conformance evaluation, and human accessibility UAT. This work supplies required accessibility content; it is not a WCAG certification or a professional accessibility audit.**
*   **Admin Excel Reference Dataset Reconciliation Foundation**: Controlled, mapping-driven server-side reconciliation foundation matching submitted project packages against staff-supplied Admin Reference `.xlsx` workbooks during browser folder import preview and staging. Includes POST `/api/imports/admin-reference/inspect` for multi-sheet/headers inspection, 1–3 composite match keys, 1–20 comparison field cross-checks, TOCTOU preview fingerprint binding, server staging re-verification, and zero raw cell persistence. ## 2. Priority 0 — Remaining Auth, Roles, and Governance Work

The explicit Supabase Auth / PostgreSQL state machine uses a two-minute durable execution lease with hashed, rotating ownership credentials: an active duplicate is an observer with zero Auth side effects, while an expired `reserved` or `invited` execution can be recovered atomically and the former owner is fenced from bind, finalize, failure and compensation. *   **Reminder Scheduling — Local/disposable technical foundation implemented**: Authorized staff can explicitly schedule and cancel future reminders for an exact active preview only after its initial email is definitely `sent`. Migration 0024 stores durable schedule/history state separately from the linked reminder notification delivery state, snapshots the original authoritative recipient, claims bounded due work concurrency-safely, and revalidates confirmation, correction, revocation, expiry, supersession, and contact changes before transport. Reminder content stores and sends no preview URL or token; it directs the participant to the original email. The existing conservative SMTP lifecycle is reused, and no terminal outcome is automatically retried. **Still pending: approved institutional cadence, production scheduler mechanism and activation, production email provider/credentials/policy, hosted acceptance, and human UAT.**
*   **Review Workflows**: Bulk review and cross-check metadata manually before preview generation.
*   **Participant Response Handling**:
    *   *Participant Confirmation* *(implemented — see "Participant Confirmation" in Section 1)*: Record an explicit participant confirmation and timestamp (auditable final sign-off), keyed to the exact preview version.
    *   *Correction Requests* *(implemented — see "Participant Correction Requests" in Section 1)*: Record correction-request comments, status, and timestamps, keyed to the exact preview version and mutually exclusive with confirmation.
*   **Admin Correction Resolution & Controlled Preview Reissue**: Authorized staff holding combined `projects.edit` AND `projects.review` authority (admin role, or dual editor+reviewer staff) can start administrative resolution on an `open` participant correction request via the service-role-only `start_participant_preview_correction_resolution` RPC (Migration 0016). Starting resolution atomically revokes the active Preview A (if its ID matches target Preview A), transitions the project from `approved` to `changes_requested`, records an auditable `approval_records` entry (`request_changes`), and marks the correction request as `in_progress`. If resolution is already `in_progress`, calling the start RPC again is idempotent and returns `ALREADY_IN_PROGRESS`. Attempting to start resolution when a conflicting active preview exists for another version of the project fails closed (`CONFLICTING_ACTIVE_PREVIEW`) without mutating project state or audit records. While `in_progress`, staff may perform required project metadata updates; ordinary preview generation remains blocked (`CORRECTION_RESOLUTION_REQUIRED`). When edits are ready, staff issue a controlled preview reissue by passing `isCorrectionReissue = true` to `POST /api/projects/[publicId]/participant-preview` (which independently enforces combined edit+review permissions at the application boundary). The 6-argument `generate_participant_preview` RPC validates that exactly one `in_progress` correction exists (failing closed with `AMBIGUOUS_CORRECTION_REQUEST` if multiple exist), captures a fresh immutable snapshot for Preview B, marks Preview B as `active`, and completes the resolution transactionally by setting the correction request status to `resolved` and setting its `replacement_preview_id` to Preview B's ID. Reissuing Preview B requires project status to be reapproved (`approved`); reapproval, email notification, and automated reminders are not included.
*   **Admin Audit Trail**: Record administrative changes and participant confirmations in logs.

## 9. Definition of Done
A backlog item is defined as done when it meets the following criteria.

### Universal Completion Requirements
1.  Acceptance criteria met.
2.  Documentation is updated.
3.  No unresolved blocking defects.
4.  Relevant security and privacy reviews completed.
5.  Verified in the appropriate environment.
6.  Evidence of completion recorded.

### Additional Requirements (Where Applicable)
*(Note: "Where applicable" applies only to requirements genuinely relevant to the specific backlog item, not to the universal definition of done).*
1.  Typed Next.js/TypeScript implementation.
2.  PostgreSQL database migrations applied to `capstone-admin-cms-staging-2026`.
3.  Unit and integration tests pass (Vitest).
4.  Accessibility compliance testing.
5.  Administrative staff UAT and staging acceptance signed off.
6.  Rollback and recovery verification completed.
7.  Institutional ownership and handover complete.

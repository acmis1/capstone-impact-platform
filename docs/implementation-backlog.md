## 1. Current Completed/Verified Baseline
*   **Prototype Recovery**: Successful database recovery (10 project records, 6 public-feed records) and poster repairs completed.
*   **Render Deployment**: Prototype web service successfully deployed from `main` branch to Render and confirmed Live.
*   **Duda Test-Site Verification**: Client-side listing and detail rendering manually verified on the Duda test-site.
*   **Admin CMS Foundation**: Modular Next.js app structure, TypeScript domain models, and 45 timestamped migrations. Earlier migrations established atomic import, review, participant-preview, correction, publication, removal, metadata-audit, staff identity, email/reminder, accessibility, password-recovery, and assistive-validation foundations. `20260828120000_assistive_worker_heartbeat.sql` adds the fail-closed dedicated-worker liveness contract after the closed non-authoritative LanguageTool finding contract. Existing historical migrations remain unchanged; repository migrations newer than the recorded hosted baseline are not represented as hosted evidence.
*   **Secure Participant Preview**: After a project reaches `approved`, authorized staff (the existing `projects.review` permission — admin/reviewer) can generate a private, token-protected, time-limited (7-day default) participant preview link from the project detail page, and revoke it.
*   **Participant Confirmation**: Beneath the rendered preview, a participant may explicitly confirm — via a plain same-origin POST form — that the project information shown in this exact preview version is correct.
*   **Participant Correction Requests**: As the mutually exclusive alternative to confirmation, a participant may instead submit a plain-text correction request describing what needs to change about the exact preview version shown.
*   **Admin Correction Resolution & Controlled Preview Reissue**: Authorized staff holding combined `projects.edit` AND `projects.review` authority can start administrative resolution on an `open` participant correction request via the service-role-only `start_participant_preview_correction_resolution` RPC (Migration 0016). Starting resolution atomically revokes Preview A, transitions project status from `approved` to `changes_requested`, records an auditable `approval_records` entry, and sets request status to `in_progress`. When edits are ready and project status is reapproved, staff reissues a preview (`isCorrectionReissue = true`), capturing a fresh snapshot for Preview B and transactionally setting correction status to `resolved` with `replacement_preview_id` referencing Preview B.
*   **Publication Readiness Gate**: Service-role-only `get_project_publication_readiness` RPC (Migration 0017) evaluates authoritative publication eligibility. A project is publication-ready ONLY IF status is `approved`, exactly one active preview exists, that exact preview is confirmed by the participant, has ZERO unresolved or open correction requests, and current canonical participant-facing project metadata and authoritative private media match the confirmed preview snapshots (order-independent media comparison). `compilePublicFeed` is hardened to include `published` projects ONLY (`approved` projects are no longer feed-eligible). Readiness is rendered read-only on the project detail page and performs no publication write itself.
*   **Publication Preparation Plan**: Admin-only, server-authoritative dry-run preparation verifies fresh publication readiness, resolves deterministic final public-media URLs, compiles existing published projects plus one exact READY approved candidate through the public allow-list, validates the proposed artifact, and reports deterministic count/hash with exact confirmation evidence. Generating the plan remains a no-write action.
*   **Controlled Publication Execution Foundation**: One server/core coordinator owns the canonical writer. It reserves a globally exclusive ledger operation before reading the exact deployment head, binds the immutable candidate and ordered membership, promotes verified private media without deleting its source, marks `WRITE_STARTED` before Storage, verifies exact served bytes, and atomically advances lifecycle/audit/snapshot/head evidence. After `WRITE_STARTED`, recovery converges forward on the bound candidate rather than restoring the old baseline. The Admin/CMS exposes the coordinator through acknowledged disposable-Local execution and a separate explicitly enabled PP1 staging/test-showcase action with exact runtime and Supabase-host identity. Live production publication and the separately authorised external Duda TEST verification are not included.
*   **Controlled Local Archive / Public-Feed Removal**: Admin-only Local execution uses the same global ledger writer, composes removal from the exact current deployment head, and removes only the requested published project. It atomically archives the project with one audit when a lifecycle transition is required, supports exact empty feeds and already-absent no-byte-change completion, preserves media evidence, and leaves ambiguous post-write work in forward recovery. Hosted/production mutation, Duda verification, and media deletion remain out of scope.
*   **Public Deployment History, Reconciliation, and Rollback — Local/disposable technical foundation implemented**: Immutable exact-byte versions/membership, an explicit head, operation events, bounded history/deployment-drift UI, baseline activation, published-but-undeployed reconciliation, durable opaque rollback preparation, explicit acknowledgement, rollback-as-new-version, and blocking `RECOVERY_REQUIRED` handling are implemented. Lifecycle remains editorial truth while the ledger is intended deployment truth; rollback does not reverse lifecycle or audits. Rollback execution requires an explicitly enabled loopback Local application and rollback-capable Local head. Hosted/production rollback, Duda verification, operational backup/DR certification, and staff UAT remain pending.
*   **Participant Preview Email Notification — Local/disposable technical foundation implemented**: Staff holding participant-preview authority may explicitly choose *Generate preview and send email*, which emails the exact freshly generated secure link to the project's authoritative `projects.participant_contact_email` (Migration 0023), supplied through the canonical `project-details.xlsx` → parser → import staging path. One transaction validates the recipient, creates the preview from its hash alone, and reserves a delivery lifecycle bound to that exact `participant_preview_id`, so an active preview can never exist without one. The raw credential remains non-persistent: it exists only in server memory and in the outgoing message, is never stored, logged or recoverable, and therefore a delivery **cannot** be retried later for the same preview — staff issue a new preview instead. The ledger records `reserved → transport_started → sent`, plus `failed` and `delivery_unknown`, under a two-minute fenced execution lease whose terminal states are immutable; an expired lease never re-grants execution, and an ambiguous post-transport outcome is reported truthfully and never resent. Exactly-once delivery is explicitly **not** claimed. Ordinary Generate Without Email is unchanged and sends zero mail. Verified on Local Supabase with 54 runtime scenarios against the Local email sink, plus 100 unit/service tests covering escaping, header safety, transport classification, ownership fencing and ambiguous outcomes. **Still pending: institutional/provider approval, production SMTP or provider selection, production credentials, an approved From address and domain, institutional email policy, hosted/staging rollout, human UAT, and reminder policy. Real delivery is disabled by default and fails closed until explicitly configured server-side.**
*   **Initial Admin Authentication Activation (Staging)**: Initial administrator authentication operationally verified in isolated staging (`capstone-admin-cms-staging-2026`).
*   **Transactional Review Actions**: Atomic PostgreSQL RPC function `public.perform_project_review_action` (Migration 0008), repository integration, API route handler, static contract tests, and comprehensive local atomicity/rollback verifications implemented and merged into `main` via PR #36.
*   **Import Batch Review Readiness & Submit-to-Review**: Server-authoritative readiness derivation surfaced on `/admin/imports/[batchId]` and project detail page. Authorized preparation staff (`projects.edit`) can select ready projects and submit them for administrative review (`draft`/`changes_requested` → `submitted`).
*   **Accessible Poster Full Text — required across the production workflow**: `project-details.xlsx` now requires both `Poster full text` (`posterText`) and `Accessibility text` (`accessibilityText`); a missing column, a blank value after trim, an unusable formula cell, or a value beyond its bounded technical ceiling is a blocking workbook error. Staff can edit both in the existing Project Metadata editor under unchanged Admin/Editor authority, stale-version protection, approval-reopen gate, and published lock, and each field diffs independently into exactly one `update_metadata` audit record. Migration 0025 forward-redefines `update_project_metadata`, `submit_import_projects_for_review`, `perform_project_review_action`, and `get_project_publication_readiness` so a blank value blocks review submission (`MISSING_POSTER_TEXT` / `MISSING_ACCESSIBILITY_TEXT`), blocks approval (`ACCESSIBILITY_CONTENT_REQUIRED`, zero status and zero audit mutation), and blocks publication readiness independently of any stored preview evidence. The participant preview renders both values before the confirmation controls, and public-feed validation rejects a public record missing either. A legacy `project.json` package may still be staged without them but cannot progress until staff supply both. **No OCR and no AI**: both values are staff-authored or imported, and nothing derives, transcribes, scores, or generates them. **Still pending: final Duda accessibility acceptance, formal WCAG conformance evaluation, and human accessibility UAT. This work supplies required accessibility content; it is not a WCAG certification or a professional accessibility audit.**
*   **Multi-Image Snapshot Gallery & Alt Text — production workflow foundation implemented**: Project packages now support an optional ordered snapshot gallery of up to 10 images using deterministic numeric gallery positions. Position 1 preserves the backwards-compatible `Snapshot image alt text` workbook field, while positions 2 through 10 use `Snapshot 2 alt text` through `Snapshot 10 alt text`. Each included gallery image must have exactly one authoritative staff-authored alt text, stored per media asset on `media_assets.alt_text_public`, with ordering preserved through `gallery_position`. Browser package preview, server-side revalidation, canonical media intent, private staging, Admin/CMS media editing, review submission, approval, immutable participant preview, confirmation staleness, publication readiness, controlled publication artifacts, and public-feed compilation all preserve the same gallery identity, numeric order, and alt text. Duplicate or invalid gallery positions, malformed or contradictory private media state, missing or oversized alt text, and stale confirmed gallery state fail closed. Participant-facing HTML renders the exact snapshotted alt text and never falls back to filenames. The public feed retains the compatibility `snapshots: string[]` projection while also exposing aligned structured gallery entries containing URL, alt text, and gallery position. **No OCR and no AI**: gallery alt text remains staff-authored and is never derived from filenames, titles, poster text, OCR, or AI. **Still pending: Duda-side consumption of the structured gallery, final Duda accessibility acceptance, formal WCAG conformance evaluation, and human accessibility UAT. This work supplies required accessibility content; it is not a WCAG certification or a professional accessibility audit.**
*   **Admin Excel Reference Dataset Reconciliation Foundation**: Controlled, mapping-driven server-side reconciliation foundation matching submitted project packages against staff-supplied Admin Reference `.xlsx` workbooks during browser folder import preview and staging. Includes POST `/api/imports/admin-reference/inspect` for multi-sheet/headers inspection, 1–3 composite match keys, 1–20 comparison field cross-checks, TOCTOU preview fingerprint binding, server staging re-verification, and zero raw cell persistence. Verified with 12 vitest unit tests, 5 API route security tests, and `verifyAdminExcelReconciliationRuntime.ts`.
*   **Local Supabase Performance & Scaling Verification Foundation**: Disposable Local Supabase scaling and storage bandwidth verification framework measuring real PostgreSQL query planning, PostgREST filtering/pagination, and Supabase Storage throughput at 100 projects/year target, with 500 and 1000 project stress datasets. Does not establish hosted/production SLOs.

## 2. Priority 0 — Remaining Auth, Roles, and Governance Work

The explicit Supabase Auth / PostgreSQL state machine uses a two-minute durable execution lease with hashed, rotating ownership credentials: an active duplicate is an observer with zero Auth side effects, while an expired `reserved` or `invited` execution can be recovered atomically and the former owner is fenced from bind, finalize, failure and compensation. *   **Admin Correction Resolution & Controlled Preview Reissue**: Authorized staff holding combined `projects.edit` AND `projects.review` authority (admin role, or dual editor+reviewer staff) can start administrative resolution on an `open` participant correction request via the service-role-only `start_participant_preview_correction_resolution` RPC (Migration 0016). Starting resolution atomically revokes the active Preview A (if its ID matches target Preview A), transitions the project from `approved` to `changes_requested`, records an auditable `approval_records` entry (`request_changes`), and marks the correction request as `in_progress`. If resolution is already `in_progress`, calling the start RPC again is idempotent and returns `ALREADY_IN_PROGRESS`. Attempting to start resolution when a conflicting active preview exists for another version of the project fails closed (`CONFLICTING_ACTIVE_PREVIEW`) without mutating project state or audit records. While `in_progress`, staff may perform required project metadata updates; ordinary preview generation remains blocked (`CORRECTION_RESOLUTION_REQUIRED`). When edits are ready, staff issue a controlled preview reissue by passing `isCorrectionReissue = true` to `POST /api/projects/[publicId]/participant-preview` (which independently enforces combined edit+review permissions at the application boundary). The 6-argument `generate_participant_preview` RPC validates that exactly one `in_progress` correction exists (failing closed with `AMBIGUOUS_CORRECTION_REQUEST` if multiple exist), captures a fresh immutable snapshot for Preview B, marks Preview B as `active`, and completes the resolution transactionally by setting the correction request status to `resolved` and setting its `replacement_preview_id` to Preview B's ID. Reissuing Preview B requires project status to be reapproved (`approved`); reapproval, email notification, and automated reminders are not included.

## 9. Definition of Done
A backlog item is defined as done when it meets the following criteria.

### Universal Completion Requirements
1.  Acceptance criteria met.
2.  Documentation is updated.
3.  No unresolved blocking defects.
4.  Relevant security and privacy reviews completed.
5.  Verified in the appropriate environment.
6.  Evidence of completion recorded.

### Additional Requirements (Where Applicable)
*(Note: "Where applicable" applies only to requirements genuinely relevant to the specific backlog item, not to the universal definition of done).*
1.  Typed Next.js/TypeScript implementation.
2.  PostgreSQL database migrations applied to `capstone-admin-cms-staging-2026`.
3.  Unit and integration tests pass (Vitest).
4.  Accessibility compliance testing.
5.  Administrative staff UAT and staging acceptance signed off.
6.  Rollback and recovery verification completed.
7.  Institutional ownership and handover complete.
